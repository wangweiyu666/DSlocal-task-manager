# W00/W01 工程原则与沿用方法

> 适用范围：W10 及之后的功能窗口、协议演进、数据库演进和 UI 接入  
> 形成依据：W00（DST1 正式规范与测试向量）和 W01（Room v3 冻结、迁移与模块拆分）  
> 基线提交：`54055c5`（W00）、`169ca26`（W01）

## 1. 核心结论

W00 和 W01 没有优先堆叠可见功能，而是先稳定两个最难返工的公共边界：

1. W00 冻结“外部数据进入应用时如何被理解”，使协议含义、错误结果和跨端样例可验证。
2. W01 冻结“数据进入应用后如何被保存和访问”，使数据库升级不丢数据，并使不同功能可以沿稳定接口并行开发。

后续窗口应继续遵循同一顺序：**先定义契约，再实现能力；先保护历史数据，再改变结构；先建立可验证边界，再接入 UI。**

## 2. 通用工程原则

### 2.1 规范是唯一事实来源，代码只是实现

- 协议字段、取值、组合约束和兼容语义先写入规范，再进入解析器。
- 数据表的职责、所有权、约束和迁移语义先写入数据库规范，再修改 Entity/DAO。
- 文档、代码和测试必须在同一个工作窗口内同步，不能让“代码事实”长期领先于“书面契约”。
- UI 文案和实现细节不能反向定义领域规则。

### 2.2 区分“协议合法”与“当前能力可用”

协议版本描述数据是否合法，应用版本描述能力是否已经实现。二者不得混为一谈。

- 合法但尚未实现的 DST1 v1 能力返回稳定的 `CAPABILITY_NOT_IMPLEMENTED`。
- 非法输入必须先返回具体协议错误，不能被“能力未实现”遮蔽。
- 从未实现变为已支持时，只更新应用能力与测试预期；除非字段或语义发生不兼容变化，否则不升级协议主版本。

这一原则同样适用于后续功能：可以先冻结接口、状态和持久化结构，再逐步开放 UI 和行为。

### 2.3 拒绝模糊容错，采用显式兼容

- 未知字段默认拒绝，不静默忽略。
- 文本、日期、枚举、集合顺序、重复值和跨字段冲突均显式校验。
- 可忽略字段必须进入明确白名单，而不是依靠宽松反序列化。
- 数据库升级必须使用连续 migration，不使用破坏性重建作为兜底。
- 兼容旧数据依靠版本化迁移和默认值语义，不依靠运行时猜测。

显式拒绝比“尽量解析”更容易跨端对齐，也能避免错误数据进入持久层后变成长期债务。

### 2.4 错误结果必须稳定、可定位、可测试

错误由三个层次组成：

- `code`：稳定且不随本地化变化，是测试和跨端协作的契约。
- `path`：定位到信封或短字段 JSON 路径。
- `message`：面向用户或开发者解释，可调整，但不作为机器契约。

当输入同时存在多个问题时，采用固定校验优先级。普通测试向量保持“一例一错”；只有专门的优先级案例才组合多个错误。这样可以避免不同实现因为遍历顺序不同而产生不一致结果。

### 2.5 数据历史优先于当前便利

- Entity 变化必须伴随数据库版本、Schema JSON、migration 和迁移测试。
- 审计日志、积分流水、结果修订等历史记录不通过级联删除抹除。
- 正常业务流程优先使用状态、归档、冲正和修订，不物理删除核心历史。
- 原子业务操作跨多个 DAO 时，必须由数据库事务包裹。
- 迁移验收不仅检查“数据库能打开”，还要检查旧字段和旧行保留、最终 Schema 匹配及外键有效。

### 2.6 定义、实例、进度与审计分离

W01 采用的模型分层应继续沿用：

- 定义保存 Dom 下发的最新配置。
- 实例保存发布时的不可变业务快照。
- 进度表保存计数、计时、正文、备注等可变执行状态。
- 流水、日志和结果修订保存可追溯历史。

后续实现重复任务、延期或历史重算时，不应直接用最新定义覆盖既有实例，也不应把当前状态当作完整历史。

### 2.7 按领域拆边界，不按页面堆逻辑

- DAO 按 Definition、Instance、Execution、Audit、Result、Reminder、Profile 等领域拆分。
- Repository/Service 用接口表达稳定能力，Room 实现负责持久化细节。
- UI 和 ViewModel 依赖接口，不直接组合跨 DAO 业务规则。
- `DstApplication` 负责装配；跨 DAO 原子性仍由数据层管理。
- Compose 页面按功能目录拆分，顶层应用文件只保留入口和导航装配。

这样做的目的不是增加抽象层数，而是让每个后续窗口拥有清晰文件所有权，并减少并行开发冲突。

### 2.8 可重复、幂等和可恢复是默认要求

- 导入以 `batchId` 防止重复应用。
- 重复任务实例应使用稳定 occurrence key 和唯一约束防重。
- 完成、撤销、积分冲正、结果重算和提醒重建都必须考虑重复调用。
- 中途失败时，事务应回滚到操作前状态；不能留下部分写入。
- 对可重建派生数据，应明确“备份”与“恢复后重新生成”的边界。

## 3. W00 使用的方法：契约驱动协议实现

### 3.1 从需求到可执行契约

实施顺序：

1. 列出对象、字段、类型、必填性、空值语义、长度和取值范围。
2. 区分 Schema 可表达约束与实现层约束。
3. 产出 `docs/dst1-schema.json`，对象默认关闭额外字段。
4. 为 Schema 之外的规则建立明确校验：真实日期、NFC、排序、跨记录唯一性、互斥字段和大小限制。
5. 定义稳定错误码、字段路径与校验优先级。
6. 修改解码器/解析器，使实现严格遵循上述契约。

### 3.2 使用共享清单驱动测试

`protocol-test-vectors/manifest.json` 是向量登记表，也是 Android 与未来 Dom 实现的共同验收入口。

每个向量应记录：

- 唯一 ID 和输入来源；
- 规范层预期结果；
- 当前 Android 能力层预期结果；
- 失败时的稳定错误码和路径。

向量分为：

- `valid/`：当前规范和当前应用均支持；
- `future-valid/`：规范合法，但当前应用尚未实现；
- `invalid/`：规范本身不合法；
- `generator`：尺寸、Unicode 或大量集合等不适合手写的确定性边界输入。

测试必须自动检查目录中的所有向量均已登记，避免新增样例却未进入统一测试。

### 3.3 边界测试方法

每条规则至少考虑以下四个点：

1. 正常值；
2. 刚好位于边界的值；
3. 刚越过边界的值；
4. 类型正确但语义非法的值。

对于封装协议，还要分层验证输入长度、Base64URL、压缩数据、CRC32、zlib、UTF-8、JSON 语法和领域字段，避免一层错误掩盖另一层错误。

## 4. W01 使用的方法：兼容性驱动数据演进

### 4.1 先冻结数据职责，再写迁移

实施顺序：

1. 盘点旧版本所有表、列、索引、外键、默认值和已有数据语义。
2. 根据后续路线图一次性补齐近期必需的公共结构，减少多个功能窗口同时改数据库核心。
3. 为每张表指定唯一主要 DAO 所有者。
4. 明确级联删除、`SET NULL`、`NO ACTION` 和业务归档策略。
5. 升级数据库版本并编写连续迁移。
6. 由 Room 编译器导出最终 Schema JSON 并纳入版本控制。
7. 使用历史 Schema 分别创建旧库，写入代表性数据，执行迁移并验证数据与约束。

### 4.2 迁移的最低验收

每条起始版本路径都必须验证：

- 能升级到当前版本；
- 旧表、旧列和代表性数据没有丢失；
- 新列默认值符合业务语义；
- Room 最终 Schema 校验通过；
- `PRAGMA foreign_key_check` 无结果；
- 应用不再依赖 `fallbackToDestructiveMigration()`。

### 4.3 用结构拆分降低后续冲突

数据库冻结与代码拆分在同一窗口完成，因为两者共同定义后续功能的工作面：

- 表与 DAO 的所有权决定数据修改边界；
- Repository/Service 接口决定领域能力边界；
- UI 目录与 ViewModel 决定页面修改边界；
- 应用装配点决定实现替换边界。

后续窗口应优先在自己的领域目录内新增实现。如果必须修改公共协议、数据库或接口，应先说明影响范围，并同步全部契约资产和测试。

## 5. 后续窗口的标准执行流程

### 5.1 开始前

1. 阅读 `docs/preview.md`、路线图、本文件及与窗口直接相关的规范。
2. 检查 Git 状态、当前分支和基线测试，确认没有误覆盖他人改动。
3. 明确本窗口的前置条件、交付物、非目标、文件所有权和验收标准。
4. 列出可能触碰的公共边界：DST1、Room Schema、领域接口、状态机、审计语义。
5. 若前置窗口未完成，不用临时代码绕过稳定边界；应先解决依赖或缩小交付范围。

### 5.2 实施中

1. 先补规范、接口和测试样例，再实现主路径。
2. 对状态变化写出允许的前态、后态、重复调用行为和失败回滚行为。
3. 对持久化变化同步 Entity、DAO、Database、migration、Schema 和测试。
4. 对协议变化同步 Schema、错误表、manifest、合法/非法/边界向量、解析器与加载测试。
5. 对跨领域操作使用 Service/Repository 协调，不在 UI 或单个 DAO 中偷偷复制规则。
6. 对临时规则明确标注替换窗口、正式语义和迁移责任，避免临时行为变成永久契约。

### 5.3 交付前

至少执行：

```powershell
./gradlew.bat testDebugUnitTest assembleDebug
git diff --check
git status --short
```

并逐项确认：

- 新增能力有正常、边界、非法和重复调用测试；
- 旧测试继续通过；
- 协议错误码与路径稳定；
- 数据库迁移覆盖所有支持的旧版本；
- 没有破坏性迁移兜底；
- 没有把领域规则复制到 Composable；
- 没有提交 APK、报告、缓存等构建产物；
- 文档准确描述已实现、未实现和刻意后置内容。

### 5.4 交接内容

每个窗口的交接至少包含：

## 6. 变更联动清单

### 6.1 修改 DST1 时必须同时检查

- `docs/dst1-schema.json`
- `docs/dst1-test-vectors.md`
- `protocol-test-vectors/manifest.json`
- 合法、非法和边界向量
- `Dst1Decoder` / `Dst1Parser` / 协议模型
- 稳定错误码与路径
- Android 统一向量加载测试
- 协议版本是否真的需要升级

### 6.2 修改 Room 结构时必须同时检查

- Entity 和索引/唯一约束/外键
- 对应领域 DAO
- `AppDatabase` 版本
- 从所有受支持旧版本开始的连续 migration
- Room 导出的 Schema JSON
- 迁移后的默认值和数据保留测试
- `PRAGMA foreign_key_check`
- 备份格式或派生数据重建策略是否受影响

### 6.3 修改领域状态或积分/结果时必须同时检查

- 状态机允许的转换
- 幂等与重复事件行为
- 事务范围
- `action_log`
- `points_ledger` 冲正而非覆盖
- `result_revision` 历史
- 导入、延期、撤销、恢复和重算的连锁影响
- UI 仅消费领域结果，不复制规则

## 7. 需要持续避免的做法

- 只改解析器，不改 Schema、向量和错误契约。
- 只增加数据库列，不提供旧版本迁移和历史数据测试。
- 用宽松解析、未知字段忽略或破坏性重建掩盖兼容问题。
- 以中文错误文案作为测试断言。
- 用最新任务定义覆盖已经发布的实例快照。
- 删除或改写审计、积分、结果修订历史来“修正”当前结果。
- 在 Composable、ViewModel 和 DAO 中各复制一份业务状态机。
- 在一个窗口顺手实现相邻窗口功能，扩大冲突面和验收范围。
- 仅解决 Git 文本冲突，不重新验证合并后的业务语义和完整测试。

## 8. 决策准则

遇到未覆盖的新问题时，按以下顺序判断：

1. 它会不会改变外部数据的含义？会则先更新协议契约和向量。
2. 它会不会改变已保存数据的结构或历史解释？会则先设计迁移和审计语义。
3. 它是不是跨多个领域的原子行为？是则放入 Service/Repository 与数据库事务。
4. 它是否可能被重复执行、重启恢复或回放？是则先定义幂等键和重复行为。
5. 它只是当前客户端尚未实现吗？是则保留规范合法性，用能力状态表达差异。
6. 它是否真的属于当前窗口？不属于则记录依赖或后置，不扩大实现范围。

这套准则的目标是让每个新增功能都落在已经稳定的协议、数据和模块边界之上，而不是再次把公共基础变成隐含且不可验证的约定。
